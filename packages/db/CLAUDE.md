# packages/db

Drizzle schema, migrations, row-level security, the database roles and the company context (ADR 0002, ADR 0003, ADR 0005, ADR 0008). PostgreSQL 17, node-postgres driver, snake_case columns from camelCase properties. Copied from Vertex Food's `packages/db` and adapted. In phase 0 it holds the general machinery only, proven on test-only fixture tables; the first tables arrive with S01, the ledger tables, the posting function and their deferred triggers with S03.

## Layout
- `src/schema/<module>.ts`: one file per owning module, exported from `schema/index.ts` (empty until S01). A platform table never has a column named `company_id` (the convention test reads that as company scope).
- `src/schema/columns.ts`: the shared column helpers (`id`, `idIsUuidV7`, `companyId`, `timestamptz`, `createdAt`, `updatedAt`, `archivedAt`). Name a column explicitly when the snake_case casing would split it.
- `src/schema/registry.ts`: every table with its owning module, scope (`company`, `platform`) and kind (`business`, `append-only`, `queue`, `draft`). It imports nothing: the migration guard loads it with Node's type stripping.
- `src/client.ts`: `createDatabase(url)`, a pool for a runtime role only: the URL's user must be `mizan_app` or `mizan_jobs` (`RUNTIME_ROLES`), so the owner never runs the application (ADR 0008). Every connection has `DATABASE_DEADLINES` (connect 5 s; per session `statement_timeout` 10 s, `lock_timeout` 5 s, `idle_in_transaction_session_timeout` 30 s, sent at connection start; a job that needs longer sets `SET LOCAL statement_timeout` in its transaction) and an `error` listener, so a lost connection fails only its transaction and is logged through `describeForLog`, without values.
- `src/company-context.ts`: `withCompany(db, companyId, work)`, one transaction with the transaction-local setting `app.company_id` (`COMPANY_SETTING`).
- `src/describe-for-log.ts`: what an unexpected error may write to the log (a code, a table, a constraint; never a message, which can quote values).
- `migrations/`: generated SQL plus custom migrations (RLS, triggers, grants, backfills). The pattern for a custom migration: `0000_foundation.sql` (`current_company_id()`, `refuse_change()`, the `pgboss` schema); `test/fixtures/guards.sql` shows a table's policy, triggers and grants. Never read or edit `migrations/meta/`.
- `scripts/setup-local.ts`: the local PostgreSQL setup (`pnpm db:setup-local`).
- `src/testing.ts` (`@vertex-mizan/db/testing`): `createTestDatabase()`, a fresh migrated database for one test run, for this package's and the apps' test global setups.
- `test/`: run against a fresh database per run (`test/global-setup.ts`), one file at a time.
  - `fixtures/schema.ts`, `fixtures/registry.ts`, `fixtures/guards.sql`: the test-only tables (a company business table, two append-only tables with a deferred balance trigger, a platform table), created in the run's database only, from the Drizzle schema through drizzle-kit, so the column helpers are what the conventions check.
  - `conventions.ts`: `checkConventions(db, registry)`, every rule of ADR 0003, 0005 and 0008 read from the catalog. `conventions.test.ts` runs it as `mizan_app` on the migrated database, then proves each rule: a mutation breaks a fixture table, a function, a schema or a role in a rolled-back transaction, and exactly that rule must fail. A rule without a mutation fails the test.
  - `invariants.test.ts`: the append-only and deferred guards as the app role, the owner and a superuser in a replica session. `company-isolation.test.ts`, `roles.test.ts`, `client.test.ts`: isolation between two companies, what each role cannot do, the pool and its deadlines.

## Roles
- `mizan_owner` runs migrations and owns every table, function and schema. It cannot bypass RLS either: with forced RLS it sees company rows only inside `withCompany`. Locally and in CI it may create databases, for the test runs. **No runtime connection uses it** (ADR 0008): `createDatabase` refuses it; the deployment checks the same.
- `mizan_app` is what the API and the worker connect as: no `BYPASSRLS`, `NOINHERIT`, only the privileges each table's custom migration grants. It cannot turn row security off (the query then fails), change a policy, trigger or function, empty a table, set `session_replication_role`, create objects or switch role (`roles.test.ts`).
- `mizan_jobs` is the worker's cross-company jobs role (ADR 0003): no `BYPASSRLS`; it will reach across companies only through policies of its own (`TO mizan_jobs`) on the tables a migration grants it. It has no grant yet; the convention test refuses any. Audited by `log_statement = 'all'` with `log_parameter_max_length = 0` on the role: every statement it runs is in the server log, its values are not; only a superuser can change either.
- `mizan_queue` is the role pg-boss runs as (`apps/worker`). It has no privilege on any `public` table; it holds `USAGE, CREATE` on schema `pgboss`, where pg-boss installs and owns its tables.
- All four exist before the first migration (cluster-wide: `pnpm db:setup-local` locally and in CI; the deployment on servers, which must also set the jobs role's two settings). No role is a member of another: `setup-local` stops if it finds a membership.

## Rules
- Changes go through `/db-migration`. Never `drizzle-kit push`, never edit a generated migration; commit the schema and its migration together; expand, then contract.
- Every table (the convention test, `test/conventions.ts`, lists each rule): in `public`, owned by `mizan_owner`; a UUIDv7 `id` with `idIsUuidV7`; `created_at`; the timestamps of its kind; a registry entry; snake_case names; no `real`, `double precision`, `money` or zoneless `timestamp`; a `*_minor` amount is `bigint` (ADR 0007); every foreign key covered by a full index. No view or materialized view (a materialized view has no RLS of its own), and no rewrite rule on a table (it could redirect or drop a write that no trigger sees). The app role never gets `TRUNCATE` (it ignores RLS), `TRIGGER`, `MAINTAIN`, `REFERENCES` or `DELETE` (archive instead); the jobs and queue roles and `PUBLIC` get nothing. No function is `SECURITY DEFINER`.
- Company tables (scope `company`): `company_id` not null, every secondary index starts with it; foreign keys between company tables are composite, `(company_id, x_id) → (company_id, id)` with `unique (company_id, id)` on the parent, because PostgreSQL checks foreign keys without RLS; the custom migration enables and forces RLS and creates the one permissive policy `company_isolation` with `USING` and `WITH CHECK (company_id = current_company_id())`, revokes `PUBLIC` and grants the app role what it needs. Any other permissive policy is refused (it would be ORed with `company_isolation`); a restrictive one only narrows and is allowed.
- `current_company_id()` reads only the transaction setting, with no fallback; `refuse_change()` refuses `UPDATE`, `DELETE` and `TRUNCATE` for every role. The convention test pins both, so a `CREATE OR REPLACE` cannot weaken them.
- Company data is read and written only inside `withCompany`, with the company from the authenticated session or the API key, never from request input. Outside it the app role sees no company rows and cannot insert any.
- Append-only tables (ADR 0005): no `updated_at` or `archived_at`; a row trigger `BEFORE UPDATE OR DELETE` and a statement trigger `BEFORE TRUNCATE` with `refuse_change()`; no role but the owner holds `UPDATE` or `DELETE`, and the app role has `SELECT, INSERT` only. The migration guard refuses `UPDATE`, `DELETE`, `TRUNCATE`, `MERGE`, an upsert's `DO UPDATE`, `DROP TABLE`, a dropped column and a column type change on them.
- Every trigger is `ENABLE ALWAYS` (ADR 0008): `CREATE TRIGGER`, then `ALTER TABLE … ENABLE ALWAYS TRIGGER …`. A check that spans rows is a constraint trigger `AFTER … FOR EACH ROW`, `DEFERRABLE INITIALLY DEFERRED`, that checks the whole entry idempotently (`fixture_entry_balances()` is the pattern). Locks are taken in one order: the company ledger head, then the period.
- Money columns (ADR 0007): `bigint` minor units (`bigint({ mode: 'bigint' })`) beside a currency column; rates as `numeric` with their base, quote and type. Never a float.

## Local database
1. `docker compose up -d` at the repository root: PostgreSQL 17 on `127.0.0.1:55417`, a disposable container (`docker compose down -v` disposes of it).
2. Copy `.env.example` to `.env` at the repository root (its fake passwords match the container).
3. `pnpm db:setup-local` (creates or updates the roles and the `vertex_mizan` database; never drops anything), then `pnpm db:migrate`.

The tests need the admin, owner, app, jobs and queue URLs: each run creates `mizan_test_<time>_<random>` as the owner, migrates it, adds the fixture tables and drops it. The superuser URL reaches that database only, for what only a superuser can try (a replica session, role attributes). Turborepo passes only the URLs listed in `passThroughEnv` of the `test` task in `turbo.json`.

Run: `pnpm --filter @vertex-mizan/db test`.
