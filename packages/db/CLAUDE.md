# packages/db

Drizzle schema, migrations, row-level security, the database roles and the company context (ADR 0002, ADR 0003, ADR 0005, ADR 0008). PostgreSQL 17, node-postgres driver, snake_case columns from camelCase properties. Copied from Vertex Food's `packages/db` and adapted. The general machinery is proven on test-only fixture tables; S01 brought the first tables (people, companies, access, the audit logs), S02 the chart of accounts, dimensions and rates, S03 the ledger, its state and the posting function.

## Layout
- `src/schema/<module>.ts`: one file per owning module, exported from `schema/index.ts`. A platform table never has a column named `company_id` (the convention test reads that as company scope): one that points at a company names it `scope_company_id` (the platform audit log: `subject_company_id`).
  - `access.ts`: Better Auth's tables (`users`, `accounts`, `sessions`, `verifications`, `two_factors`, `rate_limits`; property names are the field names its Drizzle adapter expects), `memberships`, `invitations` and the `membership_role` enum (S01).
  - `companies.ts`: `companies` (platform) and `company_settings` (company: the ledgers, fiscal year start and policy note, locked by `company_settings_lock()` once `books_started_at` is set). `SETTINGS_CURRENCY_CODES` and `SETTINGS_RATE_TYPES` are the money module's lists its checks accept (a test keeps them equal).
  - `audit.ts`: `platform_audit_entries` and `audit_entries` (company), both append-only.
  - `chart.ts` (S02): `chart_accounts` (named apart from Better Auth's `accounts`; the code shape, class, statement line and flags as checks; `CHART_STATEMENT_LINES` equals the contracts' catalogue, a test keeps them equal), `account_required_dimensions`, `account_roles` and the `account_role` enum.
  - `dimensions.ts` (S02): `dimension_types` and `dimension_values` (`VALUE_CONTRACT_KINDS`, `VALUE_EXTERNAL_SOURCES`).
  - `rates.ts` (S02): `rate_pairs` (one orientation per pair: a unique index on the sorted currencies), `exchange_rates` (append-only; one original row per pair, type and date, and each row superseded at most once, so a date's corrections form one chain) and `bulletin_holidays`; `company_settings.bulletin_days_off` holds the weekly days off.
  - `email.ts`: `email_outbox` (platform, ephemeral; owner decision 2026-10-26): the API writes an email in the transaction of its change, the worker sends and deletes it. `OUTBOX_EMAIL_KINDS` equals `EMAIL_KINDS` in contracts (a test keeps them equal).
  - `ledger.ts` (S03, ADR 0005, 0008, 0012): the append-only ledger (`posting_requests`, `journal_entries` with `sequence`, `previous_hash` and `hash`, `journal_lines` with the three amounts, `line_conversions` with each rate as used and its row, `dimension_sets` keyed by their sorted `type_id:value_id` pairs and `dimension_set_values`) and the ledger state (`ledger_heads`, `entry_number_counters`, `periods`, `period_balances`). `JOURNAL_ENTRY_SOURCES` equals `ENTRY_SOURCES` of `packages/ledger`.
- `src/schema/columns.ts`: the shared column helpers (`id`, `idIsUuidV7`, `companyId`, `timestamptz`, `createdAt`, `updatedAt`, `archivedAt`). Name a column explicitly when the snake_case casing would split it.
- `src/schema/registry.ts`: every table with its owning module, scope (`company`, `platform`) and kind (`business`, `append-only`, `ledger-state`, `queue`, `draft`, `ephemeral`). It imports nothing: the migration guard loads it with Node's type stripping.
- `src/posting/post.ts`: `post(tx, request)`, **the only writer of the ledger** (ADR 0005 invariant 11; the convention test scans every source file for another): inside `withCompany`, the posting request (a replay answers the first entry, another payload is `IDEMPOTENCY_CONFLICT`), the ledger head then the settings `FOR UPDATE`, the manual date (S03 rule 6), the SYP date, the period made open and read `FOR SHARE` (`PERIOD_CLOSED`), the lines checked and built by `packages/ledger` (a manual entry's `manualEntryLines()` and `balanceEntry()` on the role accounts, a reversal's `manualReversalLines()`), the accounts and books marked as used, the number of the fiscal year of the entry date, the dimension sets, the hash (`chainEntryValue()`), the entry, lines, conversions (none on a reversal: it read no rate), the `entry.posted` audit row and the head. A request says what to post (`PostingContent`), never posted amounts. `src/posting/reads.ts`: `readChain()` (the chain as stored, typed for `chainEntryValue()`), `rebuildPeriodBalances()` and `readPeriodBalances()`.
- `src/services/`: the transaction functions the API, the server commands and the scenario book's setup share, so a case runs through what the system runs: `companies.ts` (`createCompanyBooks`: the company, its settings and its chart template; `ledgerColumns`, `ledgersOf`), `chart.ts` (`applyChartTemplate`, `createAccount`, `lockedAccount`), `rates.ts` (`recordRate`, `ratePairFor`, `readRateRows`, `setBulletinDaysOff`, `addBulletinHoliday`, `publicationCalendar`, `rateText`). They throw `DomainError`s; `src/unique-violation.ts` (`onUniqueViolation`) answers a unique key with its code. `src/audit.ts`: `writeCompanyAudit`, `writePlatformAudit` and `AUDITED_FIELDS` (the posting function writes its own audit row; the API re-exports them).
- `src/client.ts`: `createDatabase(url)`, a pool for a runtime role only: the URL's user must be `mizan_app` or `mizan_jobs` (`RUNTIME_ROLES`), and a `user` query parameter (which node-postgres would prefer) is refused, so the owner never runs the application (ADR 0008). Every connection has `DATABASE_DEADLINES` (connect 5 s; per session `statement_timeout` 10 s, `lock_timeout` 5 s, `idle_in_transaction_session_timeout` 30 s, sent at connection start; a job that needs longer sets `SET LOCAL statement_timeout` in its transaction) and an `error` listener, so a lost connection fails only its transaction and is logged through `describeForLog`, without values.
- `src/company-context.ts`: `withCompany(db, companyId, work)`, one transaction with the transaction-local setting `app.company_id` (`COMPANY_SETTING`).
- `src/describe-for-log.ts`: what an unexpected error may write to the log (a code, a table, a constraint; never a message, which can quote values).
- `migrations/`: generated SQL plus custom migrations (RLS, triggers, grants, backfills). The pattern for a custom migration: `0000_foundation.sql` (`current_company_id()`, `refuse_change()`, the `pgboss` schema), `0002_access_guards.sql` (S01: grants per kind, forced RLS, both audit logs' triggers, the settings lock), `0004_company_settings_never_deleted.sql` (`refuse_delete()` on a business table whose deletion would undo a guard), `0009_s02_chart_guards.sql` (S02: RLS and grants, `refuse_delete()` on every business table, the guard triggers that read other rows, `new_uuidv7()` for rows a trigger makes, and the five roots and built-in dimension types every company gets from `company_settings_create_chart()` in its creation transaction, backfilled per company context), `0012_s03_ledger_guards.sql` (S03: the append-only ledger and the ledger state, the entry's immediate and deferred guards, the line's validity, the period balances written by a line trigger, the dimension sets' keys, and the ledger head of every company); `test/fixtures/guards.sql` shows a table's policy, triggers and grants. Never read or edit `migrations/meta/`.
- `scripts/setup-local.ts`: the local PostgreSQL setup (`pnpm db:setup-local`).
- `src/testing.ts` (`@vertex-mizan/db/testing`): `createTestDatabase()`, a fresh migrated database for one test run, for this package's and the apps' test global setups.
- `test/`: run against a fresh database per run (`test/global-setup.ts`), one file at a time, in one worker without isolation (`vitest.config.ts`): modules load once for the run, each file opens and closes its own pools (`connections.ts`), and `restore-env.ts` puts `process.env` back after each file. A test leaves nothing in module state.
  - `fixtures/schema.ts`, `fixtures/registry.ts`, `fixtures/guards.sql`: the test-only tables (a company business table, two append-only tables with a deferred balance trigger, a ledger-state counter with its guard, a platform business table, a platform ephemeral table), created in the run's database only, from the Drizzle schema through drizzle-kit, so the column helpers are what the conventions check.
  - `conventions.ts`: `checkConventions(db, registry, guards)`, every rule of ADR 0003, 0005 and 0008 read from the catalog, and `GUARDS`, the pinned guard functions and the required guard triggers. `conventions.test.ts` runs it as `mizan_app` on the migrated database, then proves each rule: a mutation breaks a fixture table, a function, a schema or a role in a rolled-back transaction, and exactly that rule must fail. A rule without a mutation fails the test.
  - `invariants.test.ts`: the append-only and deferred guards as the app role, the owner and a superuser in a replica session. `company-isolation.test.ts`, `roles.test.ts`, `client.test.ts`: isolation between two companies, what each role cannot do, the pool and its deadlines. `company-isolation.properties.test.ts`: ADR 0003's property (fast-check) on every company table of the registry; it fails when a company table is added without rows in it. `access.test.ts`: S01's tables (the settings lock as each role, both audit logs append-only, isolation, the checks, the ephemeral kind). `chart.test.ts`: S02's tables (the roots and built-in types, the chart checks, tree and lock after first use, roles, dimensions, the rate table and its corrections, no deletion for any role). `ledger.test.ts`: S03's ledger: `post()` (manual entries, dealt rates, replays, each refusal leaving nothing behind, reversals, numbers by fiscal year, a closed period and a close racing a posting, concurrent postings and double submits), every guard as the app role and the owner, and entries forged by hand that the guards refuse. `posting.properties.test.ts`: ADR 0005's properties of the posting function on generated sequences.

## Roles
- `mizan_owner` runs migrations and owns every table, function and schema. It cannot bypass RLS either: with forced RLS it sees company rows only inside `withCompany`. Locally and in CI it may create databases, for the test runs. **No runtime connection uses it** (ADR 0008): `createDatabase` refuses it; the deployment checks the same.
- `mizan_app` is what the API and the worker connect as: no `BYPASSRLS`, `NOINHERIT`, only the privileges each table's custom migration grants. It cannot turn row security off (the query then fails), change a policy, trigger or function, empty a table, set `session_replication_role`, create objects or switch role (`roles.test.ts`).
- `mizan_jobs` is the worker's cross-company jobs role (ADR 0003): no `BYPASSRLS`; it will reach across companies only through policies of its own (`TO mizan_jobs`) on the tables a migration grants it. It has no grant yet; the convention test refuses any. Audited by `log_statement = 'all'` with `log_parameter_max_length = 0` on the role: every statement it runs is in the server log, its values are not; only a superuser can change either.
- `mizan_queue` is the role pg-boss runs as (`apps/worker`). It has no privilege on any `public` table; it holds `USAGE, CREATE` on schema `pgboss`, where pg-boss installs and owns its tables.
- All four exist before the first migration (cluster-wide: `pnpm db:setup-local` locally and in CI; the deployment on servers, which must also set the jobs role's two settings). No role is a member of another: `setup-local` stops if it finds a membership.

## Rules
- Changes go through `/db-migration`. Never `drizzle-kit push`, never edit a generated migration; commit the schema and its migration together; expand, then contract.
- Every table (the convention test, `test/conventions.ts`, lists each rule): in `public`, owned by `mizan_owner`; a UUIDv7 `id` with `idIsUuidV7`; `created_at`; the timestamps of its kind; a registry entry; snake_case names; no `real`, `double precision`, `money` or zoneless `timestamp`; a `*_minor` amount is `bigint` (ADR 0007); every foreign key covered by a full index. No view or materialized view (a materialized view has no RLS of its own), and no rewrite rule on a table (it could redirect or drop a write that no trigger sees). The app role never gets `TRUNCATE` (it ignores RLS), `TRIGGER`, `MAINTAIN`, `REFERENCES` or `DELETE` (archive instead), except `DELETE` on an `ephemeral` table; the jobs and queue roles and `PUBLIC` get nothing. No function is `SECURITY DEFINER`.
- Company tables (scope `company`): `company_id` not null, every secondary index starts with it; foreign keys between company tables are composite, `(company_id, x_id) → (company_id, id)` with `unique (company_id, id)` on the parent, because PostgreSQL checks foreign keys without RLS; the custom migration enables and forces RLS and creates the one permissive policy `company_isolation` with `USING` and `WITH CHECK (company_id = current_company_id())`, revokes `PUBLIC` and grants the app role what it needs. Any other permissive policy is refused (it would be ORed with `company_isolation`); a restrictive one only narrows and is allowed.
- `current_company_id()` reads only the transaction setting, with no fallback; `refuse_change()` refuses `UPDATE`, `DELETE` and `TRUNCATE` for every role. **Every guard function is pinned** in `GUARDS.functions` (`test/conventions.ts`), so a `CREATE OR REPLACE` that weakens one fails the convention test; every guard trigger is listed in `GUARDS.triggers` with the events it must fire on (S01's settings lock on `UPDATE`; S03 adds the ledger's), and the test fails if it is missing, rebound, conditional, statement-level, on fewer events or no longer deferred.
- No role but the owner creates temporary tables or schemas in the database (`0000_foundation.sql` revokes `TEMPORARY` from `PUBLIC`): a table name is looked up in the session's temporary schema first, so a temporary table named like a guarded table would be read by a guard function in its place. Guard functions also name their tables with the schema (`public.journal_lines`).
- Company data is read and written only inside `withCompany`, with the company from the authenticated session or the API key, never from request input. Outside it the app role sees no company rows and cannot insert any.
- Ledger-state tables (ADR 0012): `created_at` and `updated_at`, no `archived_at`; the app role has `SELECT, INSERT, UPDATE` only; `refuse_delete()` before `DELETE` and `TRUNCATE`, and a pinned guard before `INSERT` and `UPDATE` that allows only what an append does (the head moves by one entry that follows it, a counter by one number, a period is made open, a period balance is written only at trigger depth 2 and only grows). The migration guard refuses `DELETE`, `TRUNCATE` and `MERGE` on them.
- Append-only tables (ADR 0005): no `updated_at` or `archived_at`; a row trigger `BEFORE UPDATE OR DELETE` and a statement trigger `BEFORE TRUNCATE` with `refuse_change()`; no role but the owner holds `UPDATE` or `DELETE`, and the app role has `SELECT, INSERT` only. The migration guard refuses, on them, `UPDATE`, `DELETE`, `TRUNCATE`, `MERGE`, an upsert's `DO UPDATE`, `DROP TABLE`, `RENAME`, `SET SCHEMA`, a dropped column, a type change, a generated column or expression, inheritance and partitions; anywhere, `CREATE OR REPLACE TRIGGER`, `CREATE RULE`, `DROP OWNED` and `ALTER TYPE … RENAME VALUE` (renaming enum values swaps the meaning of stored rows). No table inherits from another or is a partition (the convention test).
- A plpgsql `IF` condition ends at its first `THEN`, so a `CASE` inside one is parenthesised. A constraint trigger is a constraint: its name must not be a constraint's of the table.
- Every trigger is `ENABLE ALWAYS` (ADR 0008): `CREATE TRIGGER`, then `ALTER TABLE … ENABLE ALWAYS TRIGGER …`. A guard trigger has no `WHEN` condition and no `UPDATE OF` column list. A check that spans rows is a constraint trigger `AFTER … FOR EACH ROW`, `DEFERRABLE INITIALLY DEFERRED`, that checks the whole entry idempotently. `fixture_entry_balances()` is the pattern: the entry header states its line count, so a line added by a later transaction fails the check (a posted entry never changes); an entry the check cannot see fails; tables are schema-qualified. `sum()` skips NULLs, so a check that sums a nullable amount also counts the lines where it is NULL. A constraint trigger cannot be dropped with `DROP CONSTRAINT` (PostgreSQL requires `DROP TRIGGER`, which the guard refuses; `invariants.test.ts`). Locks are taken in one order: the company ledger head, then the period.
- A business table whose deletion would undo a guard (`company_settings`, whose row the settings lock protects) also gets `refuse_delete()` triggers before `DELETE` (row) and `TRUNCATE` (statement), `ENABLE ALWAYS`, listed in `GUARDS.triggers`.
- Ephemeral tables (S01): sessions, one-time tokens, two-factor secrets and rate-limit counters, which Better Auth deletes when they end, are used or expire, and the email outbox, whose rows the worker deletes once sent. Platform scope only, `created_at` and `updated_at` without `archived_at`, the app role holds `SELECT, INSERT, UPDATE, DELETE`, and no foreign key references one (the audit logs keep their ids without one). No company or ledger data is ever ephemeral.
- Money columns (ADR 0007): `bigint` minor units (`bigint({ mode: 'bigint' })`) beside a currency column; rates as `numeric` with their base, quote and type. Never a float.

## Local database
1. `docker compose up -d` at the repository root: PostgreSQL 17 on `127.0.0.1:55417`, a disposable container (`docker compose down -v` disposes of it).
2. Copy `.env.example` to `.env` at the repository root (its fake passwords match the container).
3. `pnpm db:setup-local` (creates or updates the roles and the `vertex_mizan` database; never drops anything), then `pnpm db:migrate`.

The tests need the admin, owner, app, jobs and queue URLs: each run creates `mizan_test_<time>_<random>` as the owner, migrates it, adds the fixture tables and drops it. The superuser URL reaches that database only, for what only a superuser can try (a replica session, role attributes). Turborepo passes only the URLs listed in `passThroughEnv` of the `test` task in `turbo.json`.

Run: `pnpm verify packages/db/test/<file>.test.ts` (some files) · `pnpm --filter @vertex-mizan/db test` (the package).
