# apps/api

NestJS 12 HTTP API with the Express adapter, a modular monolith (ADR 0002). Toolchain copied from Vertex Food's `apps/api` (plain `tsc`, no decorator metadata); logging, Standard Schema validation, the OpenAPI document, the health check and Better Auth's setup follow Vertex Hub's `apps/api`. S01 brought the access core and the first modules.

## Layout
- `src/main.ts`: loads the config from the environment, builds the app, listens on `API_HOST:API_PORT` (default `127.0.0.1:3300`).
- `src/app.module.ts`: `AppModule.forRoot(config)`: config, nestjs-pino (a request ID per request, in the `x-request-id` answer header), the database, the global `StandardSchemaValidationPipe` (422 `VALIDATION_FAILED` with the failed fields), `StandardSchemaSerializerInterceptor` and `ErrorFilter`, then the modules.
- `src/app.ts`: `configureApp(app, config)` (logger, `trust proxy` for loopback, the same-origin check, a 256 KB JSON body (`BODY_LIMIT`, S05 rule 22), the `/api` prefix except on Hub's `/v1`, no `x-powered-by`, shutdown hooks, Swagger UI at `/api/docs` outside production) and `createOpenApiDocument(app)`, which declares each route's parameter types for Swagger (this build emits no decorator metadata). Production and the tests both go through it.
- `src/core/config/`: `loadConfig(env)` (Zod; errors name the variable, never its value; `AUTH_SECRET` of 32+ characters and not the example value; `APP_URL`, the web app's origin; `DATABASE_QUEUE_URL`, the queue role, required in production, S05) and `ConfigModule` (`CONFIG` token).
- `src/core/database/`: `DatabaseModule`, one pool as `mizan_app` through `createDatabase` (`DATABASE` token), closed on shutdown. It connects on first use. `unique-violation.ts` re-exports `packages/db`'s `onUniqueViolation(write, { constraint: code })`, a unique key that decides between two writes at once answered with its code.
- `src/core/health/`: `GET /api/health` with `healthResponseSchema` from contracts: 200 when the database answers `select 1`, 503 with the same body and `database: 'down'` otherwise.
- `src/core/access/`: `company-lock.ts` (`lockCompanyForWrite`: every company write locks the company row in its transaction and refuses an archived company; `exclusive` for owner changes), the access decorators (`@Public()`, `@SignedIn()`, `@CompanyRoute(...permissions)`, `@Reauthenticated()`, `@WhileArchived()`), `@Access()` and the narrowing helpers (`signedIn`, `inCompany`, `actorOf`), the global `AccessGuard` (S01 "Rules of the guard") and `session-activity.ts` (the 30-minute idle limit, the 5-minute re-authentication window). S05: `@ApiClientRoute(...scopes)` for Hub's `/v1` (`viaApiClient`, `clientActorOf`): the guard reads `Authorization: Bearer <key>` and never a session there, and refuses a key on every other route; an active key of a client that is not archived (`401`), a company that is not archived (`COMPANY_ARCHIVED`), an address of the allow-list (`403`, logged without the key), 600 requests a minute per client (`LIMITS.apiClientPerMinute`, a counter per minute), every scope (`403`); the last use written at most once a minute. `api-keys.ts`: `newApiKey()` (`mzn_` and 40 base62 characters from the CSPRNG, unbiased), `secretHashOf()`, `clientAddress()` (an IPv4-mapped address as IPv4).
- `src/core/audit/audit.ts`: re-exports `packages/db`'s `writeCompanyAudit` (inside `withCompany`, same transaction) and `writePlatformAudit`, with `AUDITED_FIELDS`, the allow-list of fields per entity (S03 moved them there: the posting function writes its own audit row).
- `src/core/email/outbox.ts`: `queueEmail(tx, kind, recipient, data)`, the email in the transaction of its change (`email_outbox`, sent by the worker).
- `src/core/jobs/retry-queue.ts` (S05 rule 10): `RetryQueue.afterCommit(companyId, triggers)` queues `events.retry` for the worker through pg-boss as the queue role, after the commit of a change that frees held events (an event, a rate or holiday, a mapping, an account unblocked or restored); it never installs or schedules, a failure to queue is logged (the worker's daily sweep catches up), and without `DATABASE_QUEUE_URL` (the tests) it does nothing.
- `src/core/errors/`: `CodedException` (with optional `details`, such as the publication day of `RATE_MISSING`), `codeOfIssues` (a failed schema whose custom issues name one code in `params.code`, the money module's `INVALID_RATE` or `SYP_BEFORE_REDENOMINATION`, answers with it) and `ErrorFilter`: every error answer is an `ErrorResponse` with a code; a `DomainError`'s `issues` and its other facts (`details`, as text) are answered too; Express's body-parser refusals answer `413` (too large, with no code) or `VALIDATION_FAILED`, never a 500.
- `src/core/http/`: `same-origin.ts` (Hub's CSRF check), `link-tokens.ts` (one-time tokens stored as `<purpose>:<sha256>`), `cursor.ts` (pages by `(created_at, id)`; the cursor names the row and `afterCursor` compares in the database, at microsecond precision), `api-errors.ts` (`@ApiErrors(...codes)`, with `COMPANY_READ_ERRORS` and `COMPANY_WRITE_ERRORS`, the guard's answers on every company route), `api-parameters.ts` (`@ApiQueryFrom`, `@ApiParamsFrom`), `api-files.ts` (`@ApiOkProducesResponse`, a file answer).
- `src/core/limits/limits.ts`: the per-email, per-address and per-IP limits in `rate_limits`.
- `src/core/clock/today.ts`: `todayInDamascus()`, the date a manual entry's rule 6 and a copy or reversal read (S03).
- `src/core/files/`: `FileStore` (`FilesModule`, global): attachments and exports under `MIZAN_FILES_DIR` (`config.filesDir`; required in production, `.data/files/` at the repository root otherwise), one folder per company, each file named by its storage key and written whole through a temporary name, `open()` streaming a large one (an export); `attachmentTypeOf()` (the type from the first bytes: PDF, PNG, JPEG, WebP); `upload.ts`: `@AttachmentUpload()` (one `file` of at most 10 MB in memory, UTF-8 names, `ATTACHMENT_TOO_LARGE`) and `fileNameOf()`.
- `src/modules/auth/`: Better Auth (`auth.ts`: email and password, the two-factor plugin, database rate limits, the `__Host-` cookie, session hooks and the audit of its steps), `auth.controller.ts` (the five Better Auth routes S01 uses, one documented handler each, mapped to our codes; Better Auth's other paths have no route and answer `NOT_FOUND`), `account.*` (re-authentication, re-enrolment into a waiting slot, backup codes, the password reset), `password.ts` (Argon2id through `node:crypto`, with a decoy), `two-factor.ts` (codes once, backup codes, the lock).
- `src/modules/<module>/`: `me` (+ `session/session.controller.ts`), `companies`, `members`, `invitations`, `audit`: a controller and a service each (S01 "API").
- `src/modules/chart/` (S02): `accounts.*` (the tree, accounts with the lock after first use and a control account's item kind (S04), block, archive, restore, the account roles), `chart.*` (templates, apply, statement lines, the Excel export with its Arabic columns from `ar.chart`), `chart-shape.ts` (an account as the API answers it, `readChart`). `src/modules/dimensions/`: types and values (a value made by `packages/db`'s `createDimensionValue`, which the scenario setup shares, S04), Hub links. `src/modules/rates/`: pairs, rows with corrections, the rate in force through `packages/ledger`'s `policyRate` on the bulletin calendar, the calendar. The writes the scenario book's setup shares (company books, the chart template, account creation, rate recording, the calendar) are `packages/db`'s services (`src/services/`, S03), which these modules and the server commands call inside their transaction after the access checks; S05's Hub intake will call them too.
- `src/modules/drafts/` (S03): `drafts.*` (the drafts list and approval queue, save with `updatedAt` and `DRAFT_CHANGED`, preview, post, submit, withdraw, discard, approve, reject, attachments; `storeAttachment()`), `draft-shape.ts` (`readDraft`, `insertDraft`, `writeLines`), `posting.ts` (`approvalIsOn`, rule 5's `missingOf`, `contentOf`, `postDraft`: the posting function by the draft id, the draft posted and its files moved in the same transaction). `src/modules/entries/`: `entries.*` (the journal, an entry, the reversal posted or drafted by the approval switch, the copy, an entry's files, the download with `nosniff`, an account's lines with running balances summed in SQL, a rate row's entries), `entry-shape.ts` (`readEntry`, `summaryColumns`; outer columns in a raw subquery are written qualified, `journal_entries.id`, since Drizzle prints them bare). Lock order: the company row, the draft row, then `post()`'s ledger head and settings; archiving an account locks the ledger head before the account (`ACCOUNT_HAS_BALANCE`). `src/modules/integrity/` (S03 rule 19): `POST /api/integrity/check`, `packages/ledger`'s `checkIntegrity()` and `anchorResult()` over `readChain()` and `readLedgerState()` in one repeatable-read snapshot (`withCompany`'s option) with a 60-second statement limit, audited. `src/modules/exports/` (rule 21): `/api/company/exports`, the `@Reauthenticated` request (`EXPORT_IN_PROGRESS` from the one-queued key), the list, the `@Reauthenticated` 24-hour download streamed with `nosniff` (`LINK_INVALID` after), audited; the worker builds the file. Both are reads of the books, so `@WhileArchived`.
- `src/modules/open-items/` (S04): `open-items.controller.ts` (four controllers: `/api/open-items` with an item's page and a manual item's due-date change, `/api/receivables/ageing` and its export, `/api/client-funds`, `/api/clients/:valueId/statement` and its export), `open-items.service.ts` (`packages/db`'s item reads at a date and `packages/ledger`'s `ageingOf()`, `dueDateInForce()` and `fundTotals()`; a due date set from today in Damascus, the same date again a replay, `OPEN_ITEM_FROM_HUB` for a Hub item; the workbooks headed from `ar.openItems` with amounts as numbers through `spreadsheetAmount()`, audited `export.ageing` and `export.client_statement`). The drafts keep a line's `openItemId` or `newItem` (an unknown item is `VALIDATION_FAILED`); the preview names each line's item and answers each item before and after (`itemPositions()` over the balance rows); an entry's lines name their items; a copy names none. The integrity check adds `openItemProblems()` over `readOpenItemState()`; archiving an account reads `accountHasOpenItems()`.
- S05: `src/modules/api-clients/` (`/api/api-clients`: the owner's clients after a fresh code, the key's secret answered once and kept as its SHA-256, a second key for a rotation and `API_KEY_LIMIT`, revocation with a reason, a Hub client the source of every free document type and `documentTypes` moving types between clients or to none (rule 21); `revokeKeys()`, which the company's archive calls in its transaction), `src/modules/hub-api/` (`/v1/events`: the `Idempotency-Key`, `ENTRY_DATE_OUT_OF_RANGE`, `SYP_BEFORE_REDENOMINATION` and `SOURCE_NOT_ALLOWED` before anything is stored, the raw body beside its envelope to `receiveEvent()`, `201` or `202` by the event's state, one more transaction on a failure that is no refusal, then `503`; `/v1/periods/status`), `src/modules/inbox/` (`/api/inbox` with its counts, an event's detail and the four actions through `packages/db`'s inbox service; PR 4: a row's client from its payload or else its item's events (a payment's from its invoice), the `document` filter by Hub's number, the detail's `moveOn` with `firstOpenDayAfter` as the move reads it; S06: `POST /api/inbox/:id/recognise-in-open-period` (`recogniseEvent()`, `SERVICE_PERIOD_CLOSED` only) and (PR 2) `POST /api/inbox/:id/split-remainder` (`splitEvent()`, a cancelled project's remainder or an invoice after its cancellation, `revenueAmount` as `MinorUnits`); S06 PR 4: `GET /api/inbox/:id/preview?action=recognise-in-open-period|split-remainder[&revenueAmount=]` (`events.read`, `previewAction()`: what the action would lead to and post, rolled back; the action's own refusals); S06 PR 3: `src/modules/revenue/` (`GET /api/revenue/schedules`, `/schedules/:id`, `/months`, `/preview` with `recognition.read`, through `packages/db`'s revenue reads; the integrity check adds `recognitionProblems()` over `readRecognitionState()`); `/api/posting-rules` with `slotAccountFits()` and `SLOT_READERS`; a slot keeps its account while that account holds open items, `ACCOUNT_HAS_BALANCE`, the ledger head locked first). The payments' tolerance is on `PATCH /api/company`. Rates, holidays and accounts unblocked or restored queue their retries through `RetryQueue`.
- `src/admin/`: the server commands `admin:create-company` and `admin:reset-two-factor` (`commands.ts`, tested in `test/admin.test.ts`), run as the app role after `pnpm build`.
- `openapi.json`: the committed OpenAPI document (Hub and the web app read it; ADR 0006). Generated, never edited; Biome skips it.
- `test/`: `app.ts` (`createTestApp()`, the app as production builds it on the run's test database; `TEST_LOG_LEVEL` shows its logs), `global-setup.ts` (a fresh migrated database per run, the jobs role's URL for the anchors only the worker writes, and the owner role's only to close a month as S07 will, S05's move test), `browser.ts` (a cookie-keeping client with its own address and the company header; `download` reads a file answer), `people.ts` (people, sign-in, enrolment, fresh TOTP codes, companies), `guards.ts` (`expectGuarded`: `401`, `403`, `COMPANY_SWITCHED` and `COMPANY_ARCHIVED` on a list of company routes), `books.ts` (a company with Vertex Media's ledgers, the service-agency chart and today's bulletin and market rates, for the entry and draft tests; `browser.upload` sends a file), one test file per module, `architecture.test.ts` (one access decorator per route), `health.test.ts`, `openapi.test.ts`.

## Rules
- Injection is explicit: `@Inject(Token)` on every constructor parameter, classes included (no decorator metadata, so the build and Vitest behave the same; `packages/config/tsconfig/nest.json`).
- A controller declares its parameters with `{ schema }` from `@vertex-mizan/contracts`, its response with `@SerializeOptions({ schema })` and documents each answer with `@Api*Response({ standardSchema })`, then makes one call to its service. Schemas live in contracts with `.meta({ id })`.
- After changing a route or a contract it uses, regenerate the document with `pnpm --filter @vertex-mizan/api test -u` and commit `openapi.json` with the change; the test fails until it matches. CI's `pnpm check:openapi` refuses a breaking change against the base branch (ADR 0006: `/v1` is additive only).
- Every route declares exactly one access decorator; the guard fails closed and `test/architecture.test.ts` fails on a route without one. Public routes are listed in that test. A company route's handler works only inside `withCompany(db, access.company.id, …)`; the company never comes from the request (`X-Mizan-Company` is only checked against it: required on every write, and checked on a read that sends it, so a page of a company the session left gets `COMPANY_SWITCHED` instead of the other company's data).
- A list answer is serialized item by item: `@SerializeOptions({ schema: itemSchema })`, `@ApiOkResponse({ standardSchema: z.array(itemSchema) })`.
- Every change to company data writes its audit row in the same transaction; fields go through `AUDITED_FIELDS`, never a secret.
- The company context comes from the session or the API key through `withCompany`, never from input (ADR 0003). The API never connects as the owner role (ADR 0008).
- Logs through the Nest logger (pino); `authorization`, `cookie` and `set-cookie` headers are redacted. Never `console.log`.
- ESM: relative imports end in `.js`.

## Tests
Integration tests over HTTP with supertest on a fresh database per run (`DATABASE_OWNER_URL` and the role URLs, `packages/db/CLAUDE.md`); unit tests sit next to their file in `src/`. A route test covers success and the failure answers it documents. Test keys and secrets are made at run time (`test/app.ts`, `TEST_AUTH_SECRET`), never written as literals: the secret scan (`pnpm verify`, CI) refuses a literal that looks like one.

Run: `pnpm --filter @vertex-mizan/api test` · `pnpm --filter @vertex-mizan/api typecheck` · `pnpm --filter @vertex-mizan/api start` (after `pnpm build`).
